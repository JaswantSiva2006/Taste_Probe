# S7 — Live Discovery Orchestration

## 1. Product context

TasteProbe is an AI-powered cultural discovery application.

Its primary flow is:

Movie search
→ Verified movie selection
→ Qloo book retrieval
→ Candidate normalization
→ Adaptive question optimization
→ Gemini tool decision
→ User answer
→ Preference update
→ Qloo reretrieval or local reranking
→ Grounded final recommendations.

The product uses:

- Next.js 16.
- TypeScript.
- Qloo Search and Insights.
- Google Gemini 3.5 Flash-Lite.
- Deterministic question optimization.
- Replay-safe anonymous sessions.
- Optional development in-memory storage.
- Redis-backed production session storage.

Maximum questions: 3.

Maximum Qloo calls per session: 8.

Maximum agent tool calls per turn: 2.

Final recommendations: up to 5.

This segment integrates the already implemented components.

Do not rebuild them.

real Gemini.

## 5. Authoritative components

S3 owns real Qloo requests and normalization.

S4 owns sessions, revisions, locks and atomic updates.

S5 owns question validity, scoring and local reranking.

S6 owns bounded Gemini decision-making.

S7 owns orchestration.

Do not move these responsibilities into the LLM.

Do not implement duplicate logic that conflicts
with the existing components.

## 6. Core trust boundaries

Browser input is untrusted.

Signed session tokens prove identity/revision but are
not authoritative session state.

S4's session store is authoritative.

Qloo response content is external data.

Gemini function calls are untrusted requests until
application validation succeeds.

Only verified Qloo entity/tag IDs may influence
retrieval, questioning and recommendations.

Never accept arbitrary Qloo IDs generated by Gemini.

Never claim Qloo supplied an internal request ID.

## 7. Agent integration

Use S6's existing createBoundedAgent boundary.

Do not directly instantiate Gemini transport
inside discovery route handlers.

Live mode must use the real Gemini agent.

Mock mode must continue using the deterministic
mock agent.

A Gemini failure may use an explicitly labelled
deterministic fallback.

A missing or invalid Gemini configuration must
not silently activate the mock agent in live mode.

Agent results must distinguish:

LIVE_GEMINI
MOCK_AGENT
DETERMINISTIC_FALLBACK

Ensure both server traces and the response metadata
truthfully identify what happened.

## 8. Agent context

Build context from authoritative state.

Include only:

- Verified seed entity IDs.
- Current target domain.
- Confirmed positive/negative preferences.
- Current normalized recommendation summaries.
- Top eligible S5 question candidates.
- Previously asked question IDs.
- Question budget.
- Qloo usage budget.
- Authorized actions and IDs.

Do not pass:

- API keys.
- Redis tokens.
- Signed session tokens.
- Unbounded Qloo JSON.
- Complete private user state.
- Raw external request headers.

Cap descriptions and candidate counts.

Reject invalid or unsupported IDs before the model
receives the context.

## 9. Initial discovery

After entity selection:

1. Verify the seed ID server-side.
2. Create the authoritative session.
3. Retrieve book candidates through S3.
4. Normalize the results.
5. Generate S5 question candidates.
6. Score and rank them.
7. Construct S6 agent context.
8. Obtain a validated bounded agent decision.
9. Execute or present the authorized action.
10. Save the resulting session state atomically.

Initial recommendations should become available
without requiring the user to answer a question.

Do not silently substitute mock books.

If zero candidates exist, return a truthful empty
or degraded state.

Do not generate fictitious recommendations.

## 10. Agent action execution

Allowed decisions:

retrieve
enrich
ask
finish

### ASK

The selected question ID must belong to the current
S5-approved candidate set.

Use the S5-approved question wording.

Store the current question ID authoritatively.

Do not count a question twice.

Do not repeat previously asked questions.

### RETRIEVE

Use only validated intent from S6.

Execute through S3's Qloo provider.

Use verified positive entity/tag signals.

Respect remaining Qloo budget.

Never allow Gemini to construct arbitrary HTTP URLs.

### ENRICH

Allow only supported enrichment operations.

Use verified entity IDs.

If the current Qloo provider does not support the
requested enrichment capability, reject it safely
and use the bounded deterministic fallback.

Do not invent an enrichment response.

Do not expand scope by implementing a new large
tag-discovery system.

### FINISH

Stop requesting new questions.

Validate the existing shortlist.

Return only grounded candidates.

Do not fabricate recommendation explanations.

## 11. Bounded action loop

An action may trigger retrieval or enrichment.

That may justify reconsidering the next action.

But the controller must be bounded.

Enforce:

MAX_AGENT_TOOL_CALLS_PER_TURN

MAX_QLOO_CALLS_PER_SESSION

MAX_QUESTIONS

LLM_TIMEOUT_MS

QLOO_TIMEOUT_MS

Allow at most one controlled follow-up decision
after an authorized tool result, provided the
remaining budgets permit it.

If no valid further action is possible,
finish or use a deterministic grounded question.

Do not implement an open-ended recursive agent loop.

Count attempted tool executions.

A model response containing multiple calls must not
cause unauthorized additional executions.

S6's first-valid-tool policy must remain explicit.

## 12. Preference updates

An answer must match the active verified question.

Tag answers:

like:
  Confirm positive tag preference.

dislike:
  Confirm negative tag preference.

unknown:
  No inferred preference.

Entity comparisons:

prefer_a / prefer_b:
  Confirm the corresponding positive preference.

both:
  Confirm both positive preferences.

neither:
  Record appropriate negative preferences.

unknown:
  No inferred preference.

Do not infer preference from a skipped question.

Use S5's existing preference-updating logic.

Preserve S4's atomic revision handling.

## 13. Retrieval after an answer

After accepting an explicit answer:

1. Atomically reserve the valid state transition.
2. Record the explicit preference.
3. Determine whether Qloo reretrieval is justified.
4. If supported and within budget, retrieve using
   verified positive interest signals.
5. Normalize the new results.
6. Apply supported deterministic local reranking.
7. Generate new eligible questions.
8. Obtain the next bounded agent decision.
9. Commit the resulting state.
10. Return updated recommendations.

Do not claim Qloo reretrieval occurred if it did not.

For a negative tag preference, use local penalties
by default.

Only use hard Qloo exclusions when the user's
explicit intent and the verified API contract
justify that behaviour.

The existing Qloo exclusion capability must not be
used as permission to discard all negatively
associated candidates indiscriminately.

## 14. Session concurrency

S4 is responsible for replay-safe state transitions.

Preserve its atomic compare-and-swap semantics.

A stale answer must fail before paid external calls.

Two simultaneous answers using the same revision
must not both execute Qloo or Gemini work.

A simultaneous answer and finish must have at most
one successful mutation.

Do not read a session token, perform external calls,
then blindly overwrite authoritative state.

Use the existing S4 lock/reservation mechanism.

Handle:

- Lock conflicts.
- Stale revision.
- Expired session.
- Finished session.
- Provider timeout.
- Failed external operation.
- Lock expiry.

Never leave an indefinite lock.

Do not silently reset question or Qloo budgets.

## 15. Qloo usage accounting

Track actual Qloo provider attempts, including
retries where measurable.

Enforce session limits before external calls.

When a call is reserved but fails, preserve
conservative budget accounting.

Do not allow a failed tool call to create an
unbounded automatic retry cycle.

If S3's internal retry accounting prevents exact
network-attempt attribution, implement the smallest
necessary correction or clearly report the gap.

Avoid unnecessary Qloo requests after each answer.

Prefer truthful local reranking when reretrieval
provides little additional value or the budget is
nearly exhausted.

## 16. Recommendation grounding

Every final recommendation must have:

- Verified Qloo entity ID.
- Name.
- Entity type.
- Verified source evidence.
- Internal application request/correlation ID.
- Correct live/cached/fallback status.
- Optional actual Qloo description.
- Optional actual Qloo image.
- Supported explanation, if available.

Never fabricate missing descriptions or images.

Never claim an affinity is an individual's calibrated
probability of liking a book.

Preserve Qloo ordering until the application
explicitly applies a documented reranking step.

If fewer than five valid items exist, return fewer.

Do not invent candidates to fill empty slots.

## 17. Recommendation-change evidence

When preferences change, expose enough metadata
to distinguish:

QLOO_RERETRIEVAL
LOCAL_RERANK
UNCHANGED

Do not report reretrieval when only local ranking
changed.

Where appropriate, include:

- Previous top-K IDs.
- Updated top-K IDs.
- Verified preference ID responsible.
- Whether an actual Qloo request occurred.
- Internal request correlation IDs.

Avoid exposing unnecessary internal data.

An answer can legitimately leave the top-K unchanged.

Do not fabricate movement solely for the demo.

In that case, report truthful state changes.

## 18. Early stopping

Stop when:

- The user explicitly finishes.
- The question budget is exhausted.
- No valid unasked question remains.
- No useful question is available.
- The session expires.
- The relevant tool budget is exhausted.
- A verified agent decision requests finish.

A Gemini decision cannot override hard limits.

Do not keep asking questions just to reach three.

## 19. Failure handling

Qloo failure:

- Do not invent books.
- Use an existing verified shortlist if available.
- Label the response as degraded.
- Return a useful error if no verified data exists.

Gemini failure:

- Use a grounded deterministic fallback.
- Identify it as a fallback.
- Do not claim Gemini selected the question.

Redis/session failure:

- Fail closed.
- Do not continue using stale client state.

Timeout:

- Bound external operations.
- Release or expire locks safely.
- Never run an uncontrolled retry loop.

Malformed tool arguments:

- Reject before execution.
- Do not silently authorize invented IDs.
